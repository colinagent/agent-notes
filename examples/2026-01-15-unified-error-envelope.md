# Agent Note: 统一错误信封

Status: implemented

## 问题

API 层此前对同类失败给出三套形状：校验失败返回 `{ errors: [...] }`，鉴权失败返回 `{ message }`，未捕获异常直接交给框架输出纯文本。客户端要为每种状态码分别分支，重试逻辑无法区分「可重试的瞬时失败」和「永久性输入错误」。

这个决定只约束 HTTP 响应体的错误形状，不涉及错误如何记录、如何上报。

## 决策

所有 4xx/5xx 响应返回同一信封：

```json
{ "error": { "code": "validation_failed", "message": "…", "retryable": false, "details": [] } }
```

`code` 是稳定的机器可读枚举，属于公开契约，重命名等同于破坏性变更；`message` 面向人类，可随时改写；`retryable` 由抛出点显式声明，网关和客户端都不得自行推断。校验细节只放在 `details` 中，且不包含原始输入值，避免回显敏感数据。

信封在统一的错误处理中间件里组装，业务代码只抛出携带 `code`、`retryable` 的领域错误，不能自行拼装响应。

## 备选方案

**RFC 7807 Problem Details**：字段语义更标准，但它的 `type` 是 URI，团队没有可解析这些 URI 的基础设施，且现有客户端已经依赖 `code` 枚举；采用它等于同时维护两套标识。

**按状态码保留多套形状**：改动最小，但正是它让客户端无法统一处理；错误形状是跨服务契约，局部便利不值得长期分支成本。

**只在网关层归一化**：网关看不到领域错误里的 `retryable`，只能按状态码猜测，恰好放大了本决定要消除的歧义。

## 后果

- 客户端和重试逻辑只依赖一个解析器；新增错误码不需要改客户端分支。
- `code` 成为需要评审的公开契约，随意增删会破坏兼容性。
- 5xx 响应不再透出框架默认的堆栈与纯文本，排查需要依赖服务端日志与请求 ID。
